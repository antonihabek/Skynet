# `drivers/rainbow` — a Rainbow Robotics RB arm (RB3, RB5, RB10, RB16 and the rest of the series) over the control box's command and data ports

`DRY-COVERAGE-PLAN.md` item 12.E.14. A Rainbow Robotics control box (the one that runs an RB3, RB5, RB10 or RB16 arm) has two TCP ports that matter here: **the command port, 5000**, a text protocol of script lines
(`move_servo_j(jnt[...],t1,t2,gain,alpha)`, `task stop`, …) that the box answers with `The command was executed` and, later and on its own, with `info[...]`, `warn[...]` and `error[...]` lines; and **the data port,
5001**, where a `reqdata` is answered with one 580-byte state packet. The grammar is the maker's UI Script manual (6.10) and its `reqdata` Structure document (6.10), and the maker publishes a client for both
(`RainbowRobotics/rbpodo`, Apache-2.0: C++ with a Python module over it). This driver links nothing of Rainbow's: it speaks the protocol, and **the maker's client is run** against a control box written in this
repository, which is the stage's independent evidence (F118's rung 3). The maker also publishes the control box's own software as a virtual machine (the Virtual Control Box); the bridge was run against it by hand, once.

```bash
make selftest          # 944 checks: the frames, the links, how the arm is opened, the state, the commands, the stop, the motions and the session, against a simulated control box on loopback ports (needs Linux)
make check             # and the sim half of SCTS through the real ABI (37 passed)
make fetch-sdk         # rbpodo at a pinned commit, checked against its SHA-256 and built into a virtual environment of its own (RBPODO_VENDOR=where it goes); never committed
make check-layout      # this driver's text and packets against the maker's own client, which is run (103 checks; RBPODO_PYTHON=the python `make fetch-sdk` prints)
make chaos             # the link-chaos contract: the control box's two TCP connections through a relay that delays, stalls and blackholes them (30 checks)
make faultvocab        # the maker's 606-code message table as errors and as warnings, and the packet document's device error, software stop, collision, joint-word, SOS-state and mode fields (5,340 checks over 1,335 codes)
make check-vm          # the bridge once through against the maker's Virtual Control Box (12 checks; `sh sim/run-vm.sh` boots it; by hand, not in any workflow)
make check-sdk-docker  # the client half in a container that builds rbpodo at RBPODO_COMMIT (the pinned one is checked by hash; `main` is the tip, unchecked)
```

## The body

Six revolute joints, `j1` to `j6` (base, shoulder, elbow, wrist 1 to 3), in radians (the controller speaks degrees). It takes a position, one control mode, and its tier ceiling is Guest (§31.3). A position command is
one **`move_servo_j`**: the controller's own call for streaming a target, whose `t1` (the time to arrive), `t2` (the time the motion is kept after arrival), `gain` and `alpha` are the operator's (`servo`; the defaults are
those of the maker's own ROS 2 package, `t1` being the control period). The state is the packet's reference and measured angles; a velocity and an effort are not reported.

```json
{"model": "RB5-850", "host": "10.0.2.7", "simulator": false,
 "limits": [[-6.0, 6.0], [-3.0, 3.0], [-2.5, 2.5], [-6.0, 6.0], [-6.0, 6.0], [-6.0, 6.0]], "servo": {"t1": 0.02, "t2": 0.04, "gain": 0.5, "alpha": 0.5}, "payload_kg": 1.5, "rate_hz": 50}
```

* **`model`** — **required**: a Rainbow model name (`RB5-850`, `RB10-1300E`, `RB3-730ES-U`, …). The controller does not say which arm it is on, so the operator does: a joint's range and a payload's limit are the arm's.
* **`host`** — **required**, with no default and no scan (10.0.2.7 from the factory), **`port`** (5000) and **`data_port`** (5001).
* **`simulator`** — **required**: whether the controller moves an arm or only its own reference (the packet's `real_vs_simulation_mode`). The open reads the mode and refuses a claim that disagrees with it, and nothing is commanded.
* **`limits`** — **required**: six `[min, max]` pairs in radians. The maker's own URDF gives every joint the same placeholder range (plus or minus 3.14) and the manual's figure is a picture, so the range is the
  operator's, for this arm and this cell. A command outside it is refused whole.
* `payload_kg` and `payload_com_mm` (the load, told to the controller when the arm is activated and by `set_payload`), `servo`, `roles`, `rate_hz` (50, up to 100), `timeout_ms`, `stale_ms`, `open_timeout_ms`. A key the driver does not
  read is refused, naming the keys it does.

## What it never does on its own

It does not activate the arm (`mc jall init` powers it and turns the servos on), it does not change the controller between its real and its simulation mode (in the simulation "only the internal reference is changed",
and the arm does not move), it does not tell the controller a payload (the `activate` motion does, and `set_payload`), and it does not acknowledge a fault. Each is a motion (`activate`, `set_mode`, `set_payload`, `clear_faults`) that a person asks for. A command is
refused, naming the state, until the controller's mode is the one the operator said it is, the arm is activated (in the real mode), and nothing is wrong or paused.

## The stop

`task stop` (the manual spells it `halt` too): "stop any program flow or action/movement". **It does not latch on the controller** (F320): the Virtual Control Box ended a servo motion on it and started the next one at
the next `move_servo_j`, so the latch is this driver's. `emergency_stop` latches and returns and never touches the line (the RHAL says it never blocks); commands are refused from that instant, whatever the line was
doing; the reading thread writes the stop under the same lock the commands are written under, so on the wire it follows every command that was in flight and never precedes one, and writes it again if the line did not
carry it. `release_stop` clears the latch only once a reading, taken after the stop was written, shows no motion command executing; against a controller that acknowledged the stop and kept moving (the simulator can be told
to), the latch stays. `task pause` is not a stop: it was seen to leave a servo stream running. The maker documents one more way to stop, `arm_powerdown()` ("be careful with use"), which this driver never sends. It is a
**software stop**: the arm's own safety circuit is a hardware chain, and there is none on this wire.

## Faults

The state of the arm is read in every packet and the controller's lines in between. **Fail closed**: an `error[code][N]` line (the driver holds it until `clear_faults` acknowledges it, and the controller says it only once),
a device error (`op_stat_sos_flag`), a software emergency stop (`op_stat_ems_flag`), a detected collision, an error bit in a joint's word, the SOS state, and a mode the document does not list are `FAULT` with `DEGRADED`;
commands are refused. Eleven of the 606 message codes are about the stop chain in the maker's own words (60, 253 to 258, 485 to 488) and are `ESTOP`. The fault word is the first held code, and otherwise the cause the packet
gives in a band above every code of the maker's table (65536 plus a device error, 131072 plus a software stop, 196608 plus the collision value, 262144 plus the joint and the bit, 327680 plus a mode the document does not list,
393216 for the SOS state). A `warn[code][N]` line is advisory: `DEGRADED` for two seconds, with the code as the fault word, and the next command is refused once, naming the warning, because the controller says a warning after
it has acknowledged the command it is about. An arm that is paused, not activated, or in the wrong mode is `DEGRADED` with the command refused, naming the motion that changes it.

Motions (`extension`, token `vendor.rainbow.task`): `status`, `set_mode mode=real|simulation`, `activate [timeout=<s>]`, `resume [after=pause|collision]`, `clear_faults`, `set_payload kg=<kg> [x= y= z=]`,
`move <joint>=<rad> … [speed=<deg/s>] [accel=<deg/s²>] [timeout=<s>]`.

## What running it found

* **F319 — the packet's `time` is not the float second the document says**: the Virtual Control Box sends an integer that does not advance (21950 in every packet), where the document gives a float second. The driver
  reads it as the integer it is and does not use it for freshness: a reading's age is when this driver received it.
* **F320 — `task stop` does not latch and `task pause` is not a stop** (the Virtual Control Box): a servo motion ended on `task stop` and the next `move_servo_j` started it again, and a paused controller kept running a
  servo stream. The latch is the driver's, and a pause is never sent as a stop.
* **F321 — the maker's client writes six significant digits, not six decimals**: 123.456789 is sent as `123.457`, 0.00001 as `1e-05` and a negative zero as `-0`, which is C++'s default stream. The difference is pinned
  by `layout_check.py`; this driver sends six decimals in plain notation, which the simulated control box (and the maker's grammar) accept.
* **F322 — the maker's client cannot read a multi-line message whole**: `error[msg][...]` can span four lines, and the client reads the first as an error and the rest as lines of an unknown kind, so the controller's
  own explanation of a parse error is lost to its caller. This driver keeps the message whole, and `layout_check.py` pins the difference.
* **F323 — the Virtual Control Box as it boots has no power on its arm, and `move_j` goes nowhere**: `information_chunk_1` is zero, the box says `info[code][0]` (the maker's "Power Down Detected. Re-initialize the robot!") beside `info[system][halt]`, `mc jall init` times
  out, and a `move_j` is acknowledged, shows `robot_state` 3 for as long as it is watched and leaves the reference where it was, to the maker's own client as well as this driver. The `move` motion says `stopped_short`
  or an error and never `arrived` unless the packet shows the arm at the goal (`vm_check.py` holds that).

## What it cannot show, and the assumptions it makes

* **An arm or a control box.** The simulated control box was written from the maker's documents and from what the Virtual Control Box and the client were seen to do, and it is accepted by the client because it was made
  to be (F15). What it shows is the driver's own transaction budget, reading cycle, staleness bound and stop path, and the driver's bytes against the maker's client's. **No Rainbow arm and no Rainbow control box was run.**
  The Virtual Control Box is the maker's simulation, run once by hand with its arm unpowered; it moved a reference and nothing else.
* **What the controller does with a command while a fault is held.** Neither the manual nor the packet document says; the driver sends none, and answers `EPERM`.
* **Which of the 606 message codes arrive as errors and which as warnings.** The table is one table for `info`, `warn` and `error`; the classes in `drivers/fault-vocabulary.json` are this driver's reading of the texts, and
  the stop chain's eleven are chosen by their words.
* **The E-Stop bits** (`information_chunk_1` bits 3 and 5) and `op_stat_self_collision`: the document does not say which value is a pressed stop, and gives the self-collision field a bit table whose meaning is not said, so nothing decides on them; `status` reports the bits as sent.
* **Units.** The document gives angles in degrees; the open reads them in that unit and the layout check holds the packet's offsets to the client's.
* **Assumption: the 50 Hz period, the 100 ms transaction, the 0.5 s staleness bound, the 0.5-degree arrival tolerance and the 250 ms command budget.** None is the maker's.
* **Licence.** rbpodo is Apache-2.0; the driver fetches it only to run it, pinned by commit and checked by SHA-256, and commits none of it. The Virtual Control Box is the maker's software, published to its customers
  at an address that does not stay still; nothing here fetches or redistributes it.
* **The link-chaos `reset` profile is not run**, for the reason `drivers/dobot` gives: a connection the control box drops is made again within half a second while the box is still there, so the link carries data
  throughout and "outage reported" has no outage to report. `selftest.py` holds what the reset would. After a **blackhole** the stop stays latched until the driver is opened again: a stop written into a link that carried
  nothing may not have been delivered, and the driver does not release one it cannot show was taken.
